# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**PaintBucketSim** — a Unity 6 (URP, 3D) real-time GPU fluid simulation. A bucket hangs from a rope, swings/rotates in 3D, and holds paint that behaves as a dense viscous liquid, exits through bottom holes as jets/droplets, and eventually deposits onto a painted surface. The heavy lifting is a **bucket-local GPU MLS-MPM (APIC) liquid solver** running in compute shaders.

- Unity Editor version: **6000.4.7f1** (see [ProjectSettings/ProjectVersion.txt](ProjectSettings/ProjectVersion.txt)). Open the project with exactly this version.
- Render pipeline: URP 17.4. Input: new Input System (`UnityEngine.InputSystem`).
- No `.asmdef` files — all runtime code compiles into the default `Assembly-CSharp`, editor code into `Assembly-CSharp-Editor`. Root namespace is `PaintBucketSim`.
- The user is Arabic-speaking; **code and identifiers stay in English/idiomatic C#/HLSL**, but design explanations may be given in Arabic.

## Build, run, and validate

This is a Unity project — there is no CLI build/test in the usual sense. Everything runs through the Unity Editor.

- **Play the sim:** open [Assets/Scenes/SampleScene.unity](Assets/Scenes/SampleScene.unity) and press Play. Runtime keys (handled in [SimulationManager.HandleBasicInput](Assets/Scripts/PaintBucketSim/Core/SimulationManager.cs)): `P` pause, `O` single-step, `R` reset.
- **"Tests" are Editor validation runners**, not NUnit. The main one is [SimulationValidationRunner](Assets/Editor/SimulationValidationRunner.cs):
  - Interactively: menu **`Paint Bucket Sim/Run Simulation Validation`**.
  - Headless/CI: launch Unity with `-batchmode -executeMethod PaintBucketSim.Editor.SimulationValidationRunner.RunBatch` plus `-paintValidation*` flags. On finish it logs `PAINT_BUCKET_VALIDATION_PASS: ...` or `PAINT_BUCKET_VALIDATION_FAIL: ...` and calls `EditorApplication.Exit(0)` on pass / `2` on fail.
  - Common flags (parsed in `ConfigureValidationMode`): `-paintValidationSteps N`, `-paintValidationTargetParticles N`, `-paintValidationSealBucket`, `-paintValidationShakeBucket`, `-paintValidationOutflow`, `-paintValidationResting`, `-paintValidationProjection`, `-paintValidationGpuStageProfile`, plus dozens of solver-tuning overrides (`-paintValidationGridDensityEosPressureScale`, `-paintValidationRedBlackSorOmega`, `-paintValidationCellSize`, …). The flag list *is* the tuning surface — read the method before adding new ones.
  - Other `RunBatch` validators live alongside it in [Assets/Editor/](Assets/Editor/): rope grab/break, rope-bucket motion/pivot/load, and paint-surface calibration runners.
- Studio scene art is generated by editor tools (`StudioBlockoutBuilder`, `StudioArtPassV02`, `StudioPolishV03` in [Assets/Editor/](Assets/Editor/)).

When changing solver physics, the expectation is to run a validation scenario and report the measured stats (divergence before/after, `Javg`, avg/max speed, ms/substep, NaN/lost counts), not just "it compiles." The validation report string is the project's primary diagnostic instrument.

## Architecture

### Simulation loop and system ordering

[SimulationManager](Assets/Scripts/PaintBucketSim/Core/SimulationManager.cs) is the root MonoBehaviour. In `FixedUpdate` it runs `TimeStepController`-gated fixed steps, each split into N substeps. Every substep calls `StepSimulationSubstep`, which steps systems **in a strict, order-dependent sequence**:

```
Environment → Rope → Bucket → RopeBucketCoupling → Boundary → Fluid
```

Order matters: `Boundary` and `Fluid` run *after* `RopeBucketCoupling` because coupling mutates bucket position/rotation, and the fluid solver reads the moving bucket boundary. Don't reorder without understanding this coupling.

- [SimulationContext](Assets/Scripts/PaintBucketSim/Core/SimulationContext.cs) is the shared object passed to every system — it owns config references, `EnvironmentState`, and a `DiagnosticsFrame`.
- [TimeStepController](Assets/Scripts/PaintBucketSim/Core/TimeStepController.cs) owns pause / single-step / substep timing.
- Config is **ScriptableObject-driven**: systems are `MonoBehaviour`s wired via `[SerializeField]` in the scene, each fed a config asset from [Assets/Scripts/PaintBucketSim/Configs/](Assets/Scripts/PaintBucketSim/Configs/) (`SimulationConfig`, `EnvironmentConfig`, `BucketConfig`, `RopeConfig`, `PaintFluidConfig`, `GpuMpmSolverConfig`, `PaintMaterialConfig`, …). Tuning happens on `.asset` files, not in code.

### Code layout (`Assets/Scripts/PaintBucketSim/`)

- `Core/` — orchestration (`SimulationManager`, `SimulationContext`, `TimeStepController`, `Units`).
- `Systems/` — one folder per subsystem: `Environment`, `Rope`, `Bucket`, `Coupling`, `Boundary`, `Fluid`, `Diagnostics`. Each holds the `MonoBehaviour` system + its renderer.
- `Configs/` — `ScriptableObject` config definitions (the `[CreateAssetMenu]` "Paint Bucket Sim/…" assets).
- `Data/` — struct-of-arrays runtime data (`FluidParticleData` = SoA `NativeArray`s, `BucketData`, `RopeData`, `BoundaryData`).
- `Runtime/` — plain runtime state/diagnostic structs (`FluidSolverStats` carries the large set of `gpu*` diagnostic fields the validators read).
- `Jobs/` — Burst `IJob`s (`RopeJobs`, `PbfJobs`, `BoundaryJobs`, `ParticlePoolJobs`).
- `Utilities/` — e.g. spatial hashing.

### The fluid solver (the core of the project)

[PaintFluidSystem](Assets/Scripts/PaintBucketSim/Systems/Fluid/PaintFluidSystem.cs) owns the particle pool (`FluidParticleData`), generates particles inside the bucket, calibrates mass/volume/density to the configured fill fraction, and selects a solver behind the [IFluidSolver](Assets/Scripts/PaintBucketSim/Systems/Fluid/Solvers/IFluidSolver.cs) interface based on `FluidSolverArchitectureConfig.activeSolver`:

- `CpuPbf` → [CpuPbfFluidSolver](Assets/Scripts/PaintBucketSim/Systems/Fluid/Solvers/CpuPbfFluidSolver.cs) — a Burst/Jobs PBF baseline.
- `GpuSparseMpmPrototype` → [GpuMpmDenseLocalSolver](Assets/Scripts/PaintBucketSim/Systems/Fluid/Solvers/GpuMpmDenseLocalSolver.cs) — the production GPU path.

The design goal is **solver-independence**: both solvers share the same particle pool, material, particle states, and diagnostics. The C# side never owns fluid state beyond the initial upload — once running, particle/grid buffers are GPU-owned ([GpuFluidBufferSet](Assets/Scripts/PaintBucketSim/Systems/Fluid/GPU/GpuFluidBufferSet.cs)), and rendering is GPU-indirect ([GpuParticleIndirectRenderer](Assets/Scripts/PaintBucketSim/Systems/Fluid/GpuParticleIndirectRenderer.cs)).

The GPU solver is the two largest files in the repo and must be understood together:
- C# dispatch/host: [GpuMpmDenseLocalSolver.cs](Assets/Scripts/PaintBucketSim/Systems/Fluid/Solvers/GpuMpmDenseLocalSolver.cs) (~4100 lines).
- Compute kernels: [GpuDenseMpmPrototype.compute](Assets/Shaders/PaintBucketSim/GpuDenseMpmPrototype.compute) (~4650 lines), with helpers in [GpuFluidUtility.compute](Assets/Shaders/PaintBucketSim/GpuFluidUtility.compute).

**Current production pipeline** (per [Docs/MLS_MPM_BUCKET_LOCAL_FINAL_DECISION.md](Docs/MLS_MPM_BUCKET_LOCAL_FINAL_DECISION.md)): bucket-local APIC/MLS-MPM transfers → grid-density compression predictor (bounded EOS) → sparse staggered **Red-Black SOR** pressure projection → local↔world transition only at the hole/spill/jet-collar exit. For scale (validated to ~390k particles) the P2G/grid/projection stages are tiled/sparse with adaptive multi-rate and adaptive projection cadence.

### Paint surface / canvas subsystem (`Assets/PaintSim/`)

A **separate** script root from `Assets/Scripts/PaintBucketSim/`. This is the downstream deposition/canvas stage (paint film grid, deposition, evolution/drying, wet-surface rendering): [PaintSimulationHost](Assets/PaintSim/Scripts/UnityBridge/PaintSimulationHost.cs), `Stages/Surface/{PaintSurface,PaintDepositor,PaintEvolver,PaintFilmGrid}.cs`, `Rendering/PaintSurfaceRenderer.cs`, with compute in [Assets/Resources/ComputeShaders/](Assets/Resources/ComputeShaders/) (`Surface/PaintFilmBaker`, `Surface/PaintEvaporation`, `Impact/SurfaceImpact`).

## GPU / compute-shader constraints (important, learned the hard way)

These recur throughout the solver work — violating them breaks the D3D11 build:

- **D3D11 UAV limit = 8.** Keep each compute kernel at ≤8 `RWStructuredBuffer` bindings; split kernels if needed (e.g. G2P is split into a velocity/APIC kernel and a deformation kernel). Bind read-only data as `StructuredBuffer`, writable as `RWStructuredBuffer`, and avoid read/write aliasing the same resource in one kernel. Writing to a `StructuredBuffer` gives `l-value specifies const object`.
- **HLSL helper ordering:** define helper functions *before* the kernels that use them (flatten/unflatten/`IsValidCell` → projection helpers → math → bucket → pressure → kernels). Out-of-order helpers silently invalidate the kernel.
- **`ComputeShader.SetVector` with `Unity.Mathematics.float3`:** convert to `Vector4` first (see the `ToVector4` helper pattern).
- Any kernel added on the C# side must exist in the `.compute` file with a matching name, and pressure-buffer ping-pong must leave `_projectionPressureBuffer` pointing at the final buffer.

## Docs are the design record

[Docs/](Docs/) contains staged design/validation reports (`*_STAGE_G9` … `G30+`). Each documents what changed, the tuning adopted, and the measured validation results for that stage. Two documents are authoritative and can override older narrative:

- [Docs/MLS_MPM_BUCKET_LOCAL_FINAL_DECISION.md](Docs/MLS_MPM_BUCKET_LOCAL_FINAL_DECISION.md) — the settled pressure/solver architecture. It explicitly **removes** and forbids restoring the old fallbacks: particle-density EOS, F/J deformation pressure, Jacobi pressure, particle-built projection mass, and moving-world-bucket boundary velocity. Do not reintroduce these.
- [PaintBucketSim_Codex_Context_README (1).md](PaintBucketSim_Codex_Context_README%20(1).md) — long-form project background and physics direction. Useful history, but note its "solver is transitional / don't touch canvas yet" framing predates the FINAL_DECISION doc and the completed G27–G30 surface work; trust the dated stage docs and the final decision over it where they conflict.

When you make a substantive physics/solver change, follow the existing convention: update or add a `Docs/*_STAGE_*.md` with the reasoning and the validation numbers.
